## 0. 요약

현재 인사이트 게시판의 UI는 **"발행물(publication)" 포맷**이다. 정사각형 카드뉴스 썸네일 그리드, 중앙정렬 대제목, 카피라이팅된 한 줄 소개 — 이 구조는 운영자가 디자인 리소스를 들여 만든 콘텐츠에서만 성립한다.

여기에 블로그가 목표하는 콘텐츠(해프닝·삽질·TIL·5줄짜리 기록)를 넣으면 **그릇이 콘텐츠보다 커서** 작성자가 위축된다.

기획 문서가 진단한 *"나는 올리면 안 되는 공간이라는 오인"* 은 작성자 구성(공식계정 독점) 때문만이 아니라 **UI 포맷 자체가 능동적으로 만들어내고 있다.** 따라서 메뉴명만 "블로그"로 바꾸고 포맷을 유지하면 오인은 해소되지 않는다.

에디터에 대한 결론은 별도다([§9](#9-에디터-심층-평가--기술-선택-판단)): **Tiptap은 유지한다.** 부족하다고 지목된 기능(코드 하이라이팅·텍스트 링크·임시저장·마크다운 붙여넣기) 중 에디터 선택 때문에 막힌 것은 없으며, 그보다 **작성 중인 텍스트를 삭제하는 붙여넣기 버그**가 더 시급하다.

> **2026-09-19 갱신**: 위 4가지 기능과 붙여넣기 버그는 모두 해결됐다(b5a99da). 이후 슬래시 메뉴·유튜브·체크리스트·표·형광펜·콜아웃·미리보기까지 추가되어, 에디터의 남은 과제는 "블로그 작성 흐름"(발행 창·서버 임시저장·분류)과 "기술 블로그 독자 경험"(목차·코드 복사)이다 → [§11](#11-블로그-에디터-구현-계획-2026-09-19).

### 기획 문서에 대한 수정 제안 (중요)

기획 문서는 **1단계 콜드시딩을 "dev 불필요"** 로 잡았으나, 실제로는 **P0 폼 수정이 선행되어야 한다.**

DM 피치는 *"만들다가 있었던 일 3~5줄만 편하게 써주세요"* 인데, 수락한 사람이 `/insight/write`에 들어오면 실제로 마주하는 것은:

| DM 약속 | 실제 폼이 요구하는 것 |
|---|---|
| "3~5줄만 편하게" | **제목(필수)** + **한 줄 소개(필수)** + 본문(필수) |
| — | 폼 절반을 차지하는 "대표 이미지" 설정 영역 |
| — | "SYDE 인사이트 **등록**하기" 라는 제출/심사 뉘앙스의 버튼 |

시딩 대상자는 쇼케이스 업보트 상위 등록자, 즉 **가장 아까운 표본**이다. 이들이 폼 앞에서 이탈하면 재시도 기회가 없다. P0 항목은 반나절 규모 작업이므로 **DM 발송 전에 처리**할 것을 권한다.

### 1-1. "한 줄 소개"가 필수 입력 🔴 P0 → 결정: 선택 입력 + 자동 추출 (§11 3단계)

> **결정 (2026-09-19, D1)**: 한 줄 소개는 선택 입력으로 바꾼다. 비어 있으면 서버 액션(`createInsight`/`updateInsight`)이 본문 앞 120자를 추출해 저장한다. 목록 카드·검색·OG 설명이 모두 같은 값을 쓰게 하기 위함이다. 아직 구현 전이며 현재 폼은 필수 상태다.

```tsx
// insight-edit-form.tsx:67
if (!title || !summary || !contentString || contentString === '{"type":"doc","content":[]}') {
    toast.error("필수 항목을 모두 입력해주세요.");
```

- `summary`가 하드 필수. 라벨에도 빨간 `*` 표시 (`:153`)
- placeholder: *"SYDE 인사이트를 한 줄로 표현해주세요."* (`:160`)

제목을 이미 쓴 사람에게 **카피라이팅을 한 번 더 요구**한다. 운영자가 카드뉴스를 만들 때는 자연스러운 필드지만, 삽질기를 쓰려는 유저에게는 "여기는 제대로 된 글만 올리는 곳"이라는 신호다.

**개선안**
- `summary`를 선택 항목으로 변경 (validation에서 제거, 라벨의 `*` 제거)
- 비어 있으면 본문 첫 문단에서 자동 추출하여 저장 (카드/OG 설명에 계속 활용 가능)
- 라벨 문구도 완화: "한 줄 소개" → "한 줄 요약 (선택)"

### 1-2. 대표 이미지 영역이 폼의 절반을 차지 🔴 P0 → ✅ 축소 (b3456f9), 발행 창으로 이동 예정 (§11 3단계)

**개선안**

### 1-4. 임시저장이 없음 🟡 P1 → ✅ 브라우저 저장 (b5a99da, 195af4d) · 서버 저장은 §11 4단계

> **현재**: `useLocalDraft`로 localStorage 자동 저장 + 복원 배너가 인사이트·쇼케이스·클럽 글·클럽 수정·모임·프로필 소개에 적용됐다.
> **결정 (2026-09-19, D3)**: 서버 임시저장은 아래 "중기: status 컬럼" 대신 **별도 `insight_drafts` 테이블**로 한다. `insights`를 읽는 곳이 8곳(목록·상세·수정·검색·사이트맵·피드·쿼리)이고 INSERT 시 활동 피드 트리거가 돌기 때문에, status 컬럼 방식은 한 곳만 필터를 빠뜨려도 초안이 공개된다. 별도 테이블은 읽기 경로를 전혀 건드리지 않는다.

DB 스키마 전수 확인 결과 `insights` 테이블에 **draft / status / is_published 컬럼이 존재하지 않는다.**

```sql
-- supabase/migrations/20260303102100_insight_all_in_one.sql
CREATE TABLE public.insights (
    id, user_id, title, content, image_url, summary, created_at, updated_at
);
-- + slug (20260405142649), + views (20260517173500)
-- draft/status/category/tags 없음
```

긴 글을 쓰다 브라우저를 닫거나 실수로 이탈하면 **전부 소실**된다. 카드뉴스처럼 외부에서 완성해 붙여넣는 콘텐츠는 영향이 적지만, 에디터 안에서 처음부터 쓰는 블로그 글에는 치명적이다.

**개선안**
- 단기: `localStorage` 자동 저장 + 복원 (마이그레이션 불필요, 가장 저렴)
- 중기: `status` 컬럼 추가 + 임시저장 목록

## 3. 리스트 레이아웃이 블로그에 맞지 않음 🟡 P1

파일: [`insight-feed.tsx:56`](../components/insight/insight-feed.tsx), [`insight-card.tsx`](../components/insight/insight-card.tsx)

### 3-1. 정사각 썸네일 그리드 = 이미지 우선 포맷

```tsx
// insight-feed.tsx:56
<div className="grid grid-cols-1 md:grid-cols-2 lg:grid-cols-3 gap-x-6 gap-y-10 ...">

// insight-card.tsx:131
containerClassName="w-full aspect-w-1 aspect-h-1 ..."
```

**모바일 실측: 1화면 = 1글.** 정사각 썸네일이 화면 폭 전체를 차지해 카드 하나가 뷰포트를 거의 다 먹는다. 18개 글을 훑으려면 18번 스크롤해야 한다.

짧은 글을 빠르게 스캔하는 블로그 소비 패턴과 정반대다. 운영자가 만든 18개 큐레이션 글에는 성립하지만, 100개의 짧은 유저 글에는 성립하지 않는다.

### 3-2. 이미지 없는 글의 처리 — 가장 눈에 띄는 문제

```tsx
// insight-thumbnail.tsx:27
const imageUrl = src || "/default_insight_thumbnail.png";
```

대표 이미지가 없으면 **SYDE 마스코트 이미지**로 대체된다. 현재는 모든 글이 운영자 카드뉴스라 노출되지 않지만, 유저 글이 들어오는 순간:

> 3열 그리드에 **동일한 마스코트 이미지가 격자로 반복**되는 화면

이 된다. 시각적으로 매우 황량하고, "아무도 제대로 안 쓰는 게시판"처럼 보인다.

### 3-3. 제목이 1줄로 잘림

```tsx
// insight-card.tsx:151, 163
<h3 className="... line-clamp-1 overflow-hidden">{title}</h3>
<p className="... line-clamp-1">{summary || "소개 글이 없습니다."}</p>
```

프로덕션 확인: *"미국 진출 노리는 1인개발자를 위한 레딧 마…"* 처럼 잘린다. 블로그 글 제목은 카드뉴스 헤드라인보다 길고 서술적인 경향이 있어 잘림이 더 심해진다.

또한 summary 폴백 문구가 **"소개 글이 없습니다."** 인데, 1-1에서 summary를 선택으로 바꾸면 이 문구가 대량 노출된다. 결함처럼 보이므로 변경 필요.

> **2026-09-19 갱신**: 1-1 결정(D1)으로 한 줄 소개가 비면 서버가 본문에서 추출해 저장하므로, **새 글에서는 이 폴백이 사실상 노출되지 않는다.** summary가 빈 기존 글에만 해당하며, 폴백 자체를 "본문 발췌"로 바꾸면 완전히 사라진다.

### 3-4. 개선안 — 텍스트 우선 리스트로 전환

참고로 **쇼케이스는 이미 가로형 리스트 레이아웃**을 쓰고 있다(좌 사이드바 + 중앙 리스트 + 우 트렌딩). 그리드는 인사이트만의 선택이다.

블로그에 맞는 구조:

```
┌──────────────────────────────────────────────┬────────┐
│ 제목 (2줄까지 허용, 크게)                       │        │
│ 본문 발췌 2~3줄 (summary 없으면 본문에서 추출)     │ 썸네일  │
│ 아바타 · 작성자 · 3일 전 · 조회 48             │ (있을때)│
└──────────────────────────────────────────────┴────────┘
```

- 썸네일은 **우측 작은 정사각형**, 없으면 **영역 자체를 생략** (마스코트 폴백 제거)
- 제목 `line-clamp-2`, 본문 발췌 `line-clamp-2~3`
- 이미지 없는 짧은 글도 부끄럽지 않게 놓이고, 1화면에 4~6개가 들어온다

## 4. 지표 노출 — 기획 문서에 대한 반론 🟡 P1

기획 문서 7장은 4개 지표(조회·좋아요·댓글·북마크) 노출을 *"통계 노출이 약한 벨로그 대비 강점"* 으로 평가했다. **독자 관점에서는 맞지만, 작성자 관점에서는 역효과일 수 있다.**

- 신규 유저의 첫 글이 목록에 `0 0 0 0` 으로 박제된다
- 현재 프로덕션 목록에서도 **댓글 수는 거의 전부 0**이다 (18개 중 16개)
- 북마크는 전체 3개 (기획 문서 1장)

벨로그가 통계 노출을 약하게 가져가는 것은 기능 부족이 아니라 **작성자 보호 장치**일 가능성이 크다. "아무도 안 본 글"이라는 사실을 작성자 본인과 모든 방문자에게 동시에 광고하면, 두 번째 글을 쓸 동기가 사라진다.

**개선안**
- 목록 카드에서는 **조회수 + 좋아요만** 노출, 댓글·북마크는 상세 페이지에서만
- 값이 0인 지표는 **숫자를 숨기거나 아이콘만 흐리게** 처리
- 상세 페이지의 4개 지표는 그대로 유지 (이미 읽은 사람에게는 유의미)

## 5. 상세 페이지 — 읽기 경험 🟡 P1

파일: [`components/insight/insight-detail-client.tsx`](../components/insight/insight-detail-client.tsx)

### 5-1. 본문 폭이 과도하게 넓음 → ✅ 본문 768px로 제한 (c60e26a)

```tsx
// insight-detail-client.tsx:219
<div className="... w-full max-w-6xl mx-auto ...">
```

`max-w-6xl` = **1152px**. 본문이 `md:text-lg`로 이 폭에 흐르면 한 줄에 60자를 넘어간다. 장문 가독성의 적정 구간은 한 줄 40~50자, 폭으로는 **680~760px**이다.

카드뉴스 이미지 위주 글에서는 넓은 폭이 유리했지만, 텍스트 위주 블로그 글에서는 반대다.

**개선안**: 본문 섹션만 `max-w-3xl`(768px) 수준으로 제한. 헤더·댓글 영역은 현행 유지 가능.

### 5-2. 헤더가 "매거진 표지" 포맷

```tsx
// insight-detail-client.tsx:226-301
// [뒤로가기] ── [300px 정사각 썸네일] ── [더보기]
// 중앙정렬 제목 (28px)
// 중앙정렬 한 줄 소개 (16px)
// 중앙정렬 작성자
```

- 300px 정사각 썸네일이 화면 중앙을 차지하고, 그 아래 모든 요소가 중앙정렬
- 개인 기록에는 과한 격식. "이 글은 대단한 글이어야 한다"는 압박
- 썸네일 없는 글이면 마스코트 이미지가 300px로 중앙에 박힌다

**개선안**
- **좌측정렬** 제목 + 그 아래 작은 작성자 라인 (아바타 20px + 이름 + 날짜)
- 대표 이미지는 상단 와이드 배너(16:9)로 옮기거나, 없으면 생략
- 뒤로가기·더보기는 현행 위치 유지

### 5-3. 이어읽기 동선이 없음 — 프로필 전략과 직결

글 본문이 끝나면 지표 바 → 댓글 섹션이 전부다. **"이 작가의 다른 글"도, "다음 글"도, 추천도 없다.**

이 지점은 기획 문서 2~3단계의 *"프로필 = 부캐 명함"* 전략과 직접 연결된다:

- 글 하단 작가 카드(아바타 + 이름 + tagline + 최근 글 3개 + 프로필 보기)는 **프로필 개편의 저비용 선행 작업**이다
- 데이터소스가 기획 문서 2단계와 동일(`insights` 테이블 + 작성자 필터)하므로 구현 중복이 없다
- 시딩된 글에서 작가 프로필로 유입되는 동선이 생기면, 3단계 프로필 릴리즈 시 "이미 채워진 명함" 효과가 더 커진다

**개선안**: 댓글 섹션 위에 작가 카드 + 같은 작가의 다른 글 3개 배치

### 5-4. 목차(TOC) 없음 🟢 P2 → §11 5단계로 계획

긴 글에서 아쉬우나, 초기 콘텐츠는 짧은 글 위주일 것이므로 우선순위 낮음.

> **2026-09-19 갱신**: 블로그 용도에 기술 블로그·TIL이 포함되면서 헤딩 앵커·목차·코드 복사 버튼을 묶어 §11 5단계에 넣었다. velog를 쓰던 개발자가 비교하는 지점이다.

## 6. 탐색 — 정렬·필터·분류 전무 🟢 P2

### 6-1. 정렬이 최신순 하나뿐

```ts
// app/insight/insight-data-actions.ts:49
.order("created_at", { ascending: false })
```

하드코딩이고, UI에 정렬/필터 컨트롤이 **하나도 없다.**

기획 문서 3장은 벨로그 성장 동력을 *"① 창업자 영향력을 통한 첫 물꼬 ② **트렌딩·팔로우 등 플랫폼 내부의 사회적 노출**"* 로 진단했다. 그런데 **현재 게시판에 트렌딩도 팔로우도 없다.**

- 4단계의 "블로그 Pick"은 운영 리소스가 드는 반면, **정렬 토글(최신순 / 인기순)** 은 훨씬 저렴하다
- `views`, `insight_likes` 집계가 이미 조회되고 있으므로 쿼리 변경만으로 가능

### 6-2. `category` 컬럼이 아직 DB에 없음

기획 문서 6장은 *"`category` 컬럼은 DB 내부용으로만 두고 운영자가 발행 후 태깅"* 을 계획했으나, **마이그레이션 전수 확인 결과 해당 컬럼이 존재하지 않는다.** 별도 마이그레이션이 필요하다. (태그 테이블도 없음)

> **결정 (2026-09-19, D2)**: 운영자 사후 태깅 대신 **작성자가 발행 창에서 카테고리를 고르고(선택 입력, 강제하지 않음) 운영자가 나중에 고칠 수 있게** 한다. 쓰임새(해프닝·프로젝트 소개·기술·마케팅·TIL)가 분명해 작성자가 고르는 편이 정확하고, 목록 필터에 바로 쓸 수 있다. 자유 태그(`tags text[]`, 글당 5개)도 함께 추가한다. 구현은 §11 4단계.
> ⚠️ **기획 문서 6장과 달라지는 결정이므로 기획 문서도 갱신이 필요하다.**

### 6-3. 팔로우 기능이 저장소 전체에 없음

`follow` 관련 테이블·컴포넌트·쿼리가 코드베이스에 **전혀 없다.** 기획 문서가 벨로그 동력으로 지목한 두 축 중 하나가 미구현 상태다. 3단계 프로필 개편과 묶어 검토할 후보.

### 9-0. 총평

**결론: Tiptap을 유지한다.**

현재 부족하다고 지목된 4가지(코드블록 하이라이팅 · 텍스트 링크 · 임시저장 · 마크다운 붙여넣기) 중 **에디터 선택 때문에 막힌 것은 하나도 없다.** 전부 설정 누락이거나 구현 미완이며, 그중 링크는 이미 스키마에 존재하고 버튼만 없는 상태다.

반대로 아래 9-1 ~ 9-3의 심각한 문제들은 **다른 에디터로 갈아타도 똑같이 재발할 수 있는 구현 결함**이다. 즉 도구의 한계가 아니다. 지금 이관하면 이 버그들은 그대로 둔 채 마이그레이션 비용만 추가로 치르게 된다.

버전 현황: **Tiptap v3.20.1 / Next 16.1 / React 19.2** — 모두 현행 메이저. 노후화로 인한 문제가 아니다.

### 9-1. 붙여넣기가 URL을 가로챈다 — 최우선 수정 대상 🔴 → ✅ 해결 (b5a99da)

[`tiptap-editor-wrapper.tsx:45-64`](../components/common/tiptap-editor-wrapper.tsx)

```js
const text = event.clipboardData?.getData("text/plain");
if (text) {
  try {
    const url = new URL(text);
    if (url.protocol === "http:" || url.protocol === "https:") {
      const secureUrl = upgradeToHttps(text) || text;
      view.dispatch(
        view.state.tr.replaceSelectionWith(      // ← 선택 영역을 "대체"
          view.state.schema.nodes.linkPreview.create({ src: secureUrl }),
        ),
      );
      return true;                               // ← 기본 붙여넣기 차단
    }
```

클립보드 내용이 URL 하나면 **조건 없이** 블록형 링크프리뷰 카드로 치환된다. 결과적으로 세 가지 시나리오가 모두 깨진다.

| 사용자 의도 | 실제 결과 |
|---|---|
| 텍스트 선택 → URL 붙여넣기 (링크를 거는 보편적 제스처) | **선택한 텍스트가 삭제되고** 카드로 대체됨 |
| 문장 중간에 URL 붙여넣기 ("자세한 건 ⟨URL⟩ 참고") | 문단이 쪼개지고 그 자리에 블록 카드 삽입 |
| URL을 일반 텍스트로 입력 | 불가능 |

`replaceSelectionWith`는 선택 영역을 교체하며, `linkPreview`는 `group: 'block', atom: true`인 블록 노드이므로 문단 중간에 삽입되면 문단이 분할된다.

**링크 버튼이 없는 것보다 이 동작이 더 나쁘다.** 버튼이 없으면 사용자는 "선택 후 붙여넣기"라는 대체 경로를 시도하는데, 그 경로가 작성 중인 텍스트를 파괴한다. 시딩 작가가 첫 글에서 이 경험을 하면 두 번째 글은 없다.

링크프리뷰 카드 기능 자체는 유지할 가치가 있다. 트리거 조건만 좁히면 된다.

**개선안**
```
선택 영역이 있음        → 선택 텍스트에 링크 마크 적용
빈 문단에 단독 붙여넣기  → 링크프리뷰 카드 (현행 동작)
문장 중간에 붙여넣기     → 인라인 링크 또는 일반 텍스트
Shift+붙여넣기          → 항상 일반 텍스트
```

### 9-3. 키 입력 1회당 문서 전체를 4번 순회한다 🟡 → ✅ 해결 (b5a99da)

```tsx
// tiptap-editor-wrapper.tsx:85-87
onUpdate: ({ editor }) => {
  onContentChange(editor.getJSON());      // ① 문서 전체 직렬화
},

// tiptap-editor-wrapper.tsx:90-102
useEffect(() => {
  const currentContent = editor.getJSON();  // ② 또 직렬화
  const isContentSame =
    JSON.stringify(initialContent) === JSON.stringify(currentContent);  // ③④ 문자열화 2회
  ...
}, [editor, initialContent]);
```

`onUpdate` → 부모 `setContent` → `initialContent` prop이 새 객체 → effect 의존성 변경 → effect 재실행. 이 사이클이 **타이핑 한 글자마다** 돈다.

타이핑 1회당 **문서 전체 순회 2회 + 전체 문자열화 2회.**

현재처럼 짧은 큐레이션 글에서는 체감되지 않지만, 목표하는 장문 회고·TIL에서는 입력 지연이 발생한다. 무한 루프는 아니다(내용이 같아 `setContent`가 호출되지 않음). 순수한 낭비다.

**개선안**: `onUpdate` 디바운스(300ms) + 외부에서 주입된 내용인지 판별하는 플래그로 effect 재실행 차단

### 9-6. 마크다운 — 타이핑은 되고, 붙여넣기만 안 된다 → ✅ 해결 (b5a99da)

**이미 동작하는 것** (StarterKit 기본 입력 규칙):

| 입력 | 결과 |
|---|---|
| `# ` `## ` `### ` | 제목 1/2/3 |
| `- ` `* ` | 불릿 목록 |
| `1. ` | 번호 목록 |
| `> ` | 인용구 |
| ` ``` ` | 코드블록 |
| `**굵게**` `*기울임*` `~~취소선~~` `` `코드` `` | 인라인 서식 |
| `---` | 구분선 |

**동작하지 않는 것**: 완성된 마크다운 문서를 **통째로 붙여넣기**. 입력 규칙은 타이핑 시에만 발동하고 붙여넣기에는 적용되지 않으므로, `# 제목`은 리터럴 텍스트로 들어간다.

노션·옵시디언·ChatGPT/Claude에서 초안을 작성해 옮겨오는 경로가 막히므로 중요도는 높다.

> 단, **노션·구글독스·웹페이지에서 복사한 내용은 HTML로 전달되어 서식이 정상 유지된다.** 깨지는 것은 생(raw) 마크다운 텍스트 경로 한정이다.

**개선안**: `handlePaste`에서 plain text가 마크다운 패턴을 포함하면 `marked`/`markdown-it`으로 HTML 변환 후 `insertContent`. 오탐 방지를 위해 "붙여넣은 서식 되돌리기" 토스트 제공 권장.

### 9-8. 읽는 쪽 — 뷰어가 에디터를 통째로 로드한다 🟡 → ✅ 해결 (c60e26a)

이것은 작성 경험이 아니라 **독자 경험** 문제이며, 블로그에서는 독자 수가 작성자 수를 압도하므로 영향 범위가 크다.

[`tiptap-viewer.tsx`](../components/common/tiptap-viewer.tsx)는 읽기 전용 콘텐츠를 렌더링하기 위해 **ProseMirror 에디터 인스턴스를 클라이언트에 생성**한다.

```tsx
const editor = useEditor({
  extensions: commonTiptapExtensions,   // 에디터용 확장 전체
  content: content as object | undefined,
  editable: false,                       // ...읽기 전용인데
});
```

그런데 [`tiptap-server-extensions.ts`](../components/common/tiptap-server-extensions.ts)에 **서버에서 완성된 HTML을 생성하는 경로가 이미 존재한다**(`getInitialHtmlFromTiptap`). 상세 페이지는 이 HTML을 먼저 그린 뒤, 마운트되면 숨기고 Tiptap 뷰어로 교체한다:

```tsx
// insight-detail-client.tsx:309-318
{initialHtml && (
  <div className={cn("prose max-w-none",
    isMounted && "absolute opacity-0 pointer-events-none -z-10 w-0 h-0 overflow-hidden")}
    dangerouslySetInnerHTML={{ __html: initialHtml }} />
)}
<div className={cn(!isMounted ? "hidden" : "block")}>
  <TiptapViewer content={parseContent(insight.content)} />
</div>
```

**동일한 콘텐츠를 두 번 렌더링**하고 있으며, 모든 독자에게 에디터 번들이 전송된다.

**개선안**: 링크프리뷰 카드와 이미지 리사이즈 표시만 경량 React 컴포넌트로 분리하고, 본문은 서버 HTML 렌더링으로 일원화. 상세 페이지 JS 페이로드가 크게 줄고 초기 렌더 깜빡임도 사라진다.

| **BlockNote** | Tiptap/ProseMirror **위에 얹은** 노션형 레이어 | Tiptap을 버리는 선택지가 아님. 슬래시 커맨드·드래그 핸들 기본 제공은 매력적이나 저장 포맷이 자체 블록 JSON이라 마이그레이션 필요 |
| **Novel** | Tiptap 기반 + AI 자동완성 | 동일하게 Tiptap 위 레이어 |
| **Plate** | Slate 기반 | Slate는 한글 IME(조합 입력) 관련 이슈 이력이 있어 한국어 서비스에 리스크 |
| **Lexical** | Meta 개발, 독립 구현 | 성능은 우수하나 생태계가 Tiptap보다 작고, 이관 비용 대비 이득이 불분명 |
| **마크다운 (CodeMirror 등)** | 벨로그 방식 | **유일한 실질적 대안** |

"위지윅을 버린다"는 선택지의 실체는 **마크다운 에디터 하나**다. 나머지는 대부분 결국 ProseMirror/Tiptap 위에 서 있다.

#### 마크다운 전환 손익

**얻는 것**
- 마크다운 붙여넣기 문제가 원천 소멸
- 코드블록이 자연스러움
- 개발자 친화적
- 저장 포맷이 단순 텍스트

**잃는 것**
1. **기존 66개 글이 전부 Tiptap JSON.** 변환은 가능하나 `linkPreview` 카드와 이미지 리사이즈 크기 정보는 **손실**된다
2. **커스텀 노드 재구현 필요** — 링크프리뷰 카드, 이미지 리사이즈. 현재 정상 동작 중인 기능들이다
3. **타겟과 충돌.** SYDE는 "1인개발자·**솔로프리너**"가 대상이다. 기획 문서 6장이 *"카테고리 선택조차 강제하지 않음 — 진입장벽 최소화"* 를 원칙으로 세웠는데, 비개발자에게 마크다운은 그보다 훨씬 큰 장벽이다
4. 이미지 업로드 파이프라인을 새 에디터에 다시 연결해야 한다

#### 판단

> 부족한 4가지는 **모두 Tiptap 안에서 해결되고**, 심각한 3가지는 **Tiptap을 벗어나도 해결되지 않는다.**
> 이관은 문제를 해결하지 않고 비용만 추가한다.

**향후 옵션**: 개발자 유입이 실제로 늘어 마크다운 요구가 커지면, 갈아타는 대신 **"마크다운 모드" 토글**을 얹으면 된다. 입력만 마크다운으로 받고 저장 시 Tiptap JSON으로 변환하는 방식이라 기존 글과 공존한다. 트리거는 2차 리네이밍과 동일한 지표(고유 작성자 20명 / 월 15건) 도달 시점에 재검토.

> 작성일: 2026-09-16
> 대상: §9 개선사항 반영 후의 인사이트 작성 폼 + 에디터 + 발행 화면

> 제약: 작성 페이지는 로그인 필요 → 동일 폼을 렌더링하는 임시 페이지로 검토(검토 후 삭제). 이미지 업로드는 인증 필요로 기존 이미지 URL로 대체.

### 10-0. 총평

**기능은 거의 갖췄지만, "처음 쓰는 사람"을 위한 다듬기가 부족하다.**

기획 배경의 목표는 *"3~5줄만 편하게"*, 비개발자 솔로프리너 포함, 오픈챗 기반 모바일 유입이다. 이 기준에서 보면 가장 큰 문제는 에디터 엔진이 아니라 **(1) 기능이 있어도 사용자에게 보이지 않는 것**, **(2) 에디터를 둘러싼 폼 구조가 본문을 밀어내는 것**이다.

잘 된 점: §9에서 바꾼 붙여넣기(URL·마크다운·다중 이미지)와 임시저장 복원은 실제 사용 흐름에서 자연스럽다. 코드 하이라이팅은 에디터와 독자 화면이 동일하다. 독자 화면에서 리사이즈 이미지 크기·링크프리뷰 카드가 운영 데이터로 정상 렌더링됨을 확인했다(§9-8 검증 완료).

### 10-2. 사용성·직관성 🟡

**10-2-1. 첫 화면에 본문 입력 영역이 없다**

| 환경 | 뷰포트 높이 | 본문 영역 시작 위치 |
|---|---|---|
| 데스크톱 1024×720 | 720px | **763px** |
| 모바일 375×812 | 812px | **639px** |

제목(필수)·한 줄 소개(필수)·대표 이미지(180~240px 블록)가 먼저 화면을 차지한다. 사용자가 이 페이지에 온 목적인 "쓰기"가 스크롤해야 보인다. §1-1·1-2의 P0 폼 개편과 같은 문제의 다른 측면이다.

**10-2-2. 모바일 툴바 60%가 숨겨져 있다**

- 툴바 전체 폭 860px 중 **341px만 노출**, 스크롤바 숨김·페이드 등 단서 없음
- 노출 순서: 실행취소 · 다시실행 · B · I · U · S · 링크 · **정렬 3개** → 이미지·목록·제목은 화면 밖
- 버튼 높이 **32px** (권장 터치 영역 44px 미달)

**10-2-3. 툴바 20개 버튼이 동일 비중으로 나열됨**

- `H1/H2/H3`, `<>`(코드블록) 표기는 비개발자에게 의미 전달 불가
- 본문 내 `H1`은 글 제목과 위계가 충돌(SEO상 h1 중복)
- 정렬(좌/중/우)은 블로그에서 사용 빈도가 낮은데 앞쪽에 배치

**10-2-4. 발행 실패 시 어떤 항목이 문제인지 알려주지 않음**

"필수 항목을 모두 입력해주세요." 토스트만 표시. 누락 필드 강조·포커스 이동·스크롤이 없다.

**10-2-5. 숨은 기능을 발견할 방법이 없음**

`## `, `- `, `> `, ` ``` ` 마크다운 단축 입력과 `Cmd+B/I/U`는 동작하지만 안내가 없다. 링크의 사실상 표준 단축키인 `Cmd+K`는 미지원.

**10-2-6. 텍스트 선택 시 서식 메뉴가 없음**

서식을 바꾸려면 항상 상단 툴바로 이동해야 한다. 모바일에서는 해당 버튼이 툴바 밖에 숨어 있을 수 있다.

**10-2-7. 이미지 경험이 블로그에 맞지 않음**

- 삽입 시 기본 **왼쪽 정렬**
- 정렬 컨트롤이 작은 점선 박스 + 아이콘 3개로 조작이 어려움
- **캡션 없음** — 운영 데이터를 보면 운영자도 "출처:" 문단을 가운데 정렬·이탤릭으로 매번 수동 작성 중

**10-2-8. 인라인 코드 버튼 없음** — TIL·기술 글의 빈출 서식

- **메뉴 그룹과 항목**

- **URL 입력창**

  - 툴바 "더보기"에도 유튜브·링크 카드를 추가한다.
- **메뉴 위치**: 메뉴가 떠 있는 채로 스크롤하면 위치가 어긋나므로 스크롤 시 `clientRect`로 위치를 다시 계산한다.

### 11-5. 4단계 — 서버 임시저장·카테고리·태그 (2.5~3일, 마이그레이션 포함)

**마이그레이션** (`supabase/migrations/2026MMDD_insight_drafts_category_tags.sql`)

```sql
create table public.insight_drafts (
  id uuid primary key default gen_random_uuid(),
  user_id uuid not null references public.profiles(id) on delete cascade,
  insight_id uuid references public.insights(id) on delete cascade, -- 발행된 글을 수정 중일 때
  title text not null default '',
  summary text, content jsonb, image_url text,
  category text, tags text[] not null default '{}',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
create unique index on public.insight_drafts (user_id, insight_id) where insight_id is not null;
-- RLS: select/insert/update/delete 모두 auth.uid() = user_id

alter table public.insights
  add column category text check (category in ('story','launch','tech','growth','til')),
  add column tags text[] not null default '{}';
create index on public.insights using gin (tags);
create index on public.insights (category, created_at desc);
```

- 카테고리 코드: `story` 해프닝·회고 / `launch` 프로젝트 소개 / `tech` 기술 / `growth` 마케팅·그로스 / `til` TIL.
- `insights`를 읽는 8곳은 수정하지 않는다(D3의 핵심).

**저장은 두 겹**

- 1겹(localStorage): 지금처럼 1초 디바운스. 오프라인에서도 남는다.
- 2겹(서버): 서버 액션 `saveInsightDraft`.
  - 입력이 5초 멈추거나 `visibilitychange`·`pagehide` 때 저장한다.
  - 첫 저장 시 `router.replace`로 주소를 `/insight/write?draft=<id>`로 바꿔 새로고침해도 이어 쓴다.
- 상단 바 상태: `저장 중…` / `저장됨 14:02` / `오프라인 · 이 기기에만 저장됨`.
- 서버와 브라우저 저장본이 다르면 `updated_at`이 최근인 쪽을 불러오고, `DraftRestoreBanner`에 비교 결과를 보여준다.
- 발행: `createInsight`에 `draftId`를 넘기면 insert 후 초안을 삭제한다. 삭제가 실패해도 발행은 유효하다.
- 명시적 "임시저장" 버튼도 둔다(tistory·네이버 사용자가 찾는 버튼).

**임시저장 목록**

- 상단 바 `임시저장 N` 버튼 → 목록 창. 항목마다 제목("제목 없음" 대체), 수정 시각, 본문 앞부분, 삭제.
- 사용자당 초안 50개 제한(서버 액션에서 확인).

**발행 창의 카테고리·태그**

- 카테고리: 칩 5개 중 선택(선택 입력).
- 태그: Enter·쉼표로 추가. 최대 5개, 태그당 20자. 앞뒤 공백 제거, 소문자화, 중복 제거.
- 상세 페이지: 제목 위 카테고리, 본문 아래 태그 칩.
- 목록의 카테고리 필터는 §6(탐색) 작업과 묶는다.

### 11-6. 5단계 — 기술 블로그 독자 경험 (1.5일, 인사이트 상세)

- **헤딩 앵커**
  - `getInitialHtmlFromTiptap` 앞 단계에서 문서를 한 번 훑어 헤딩마다 `id`를 붙이고 목차 데이터 `[{ level, text, id }]`를 만든다. `id`는 한글을 유지하고 공백만 `-`로 바꾸며, 중복되면 `-2`를 붙인다.
  - `getRenderedArticle(content) → { html, toc }`를 추가하고 기존 함수는 유지한다.
  - 서버 heading 설정에 `id` 속성을 추가하고, 마우스를 올리면 `#` 링크가 보이게 한다. 고정 헤더에 가리지 않도록 `scroll-margin-top`을 준다.
- **목차** (`components/insight/article-toc.tsx`)
  - 헤딩이 3개 이상일 때만 표시한다.
  - xl 이상: 본문 오른쪽 고정 목차, `IntersectionObserver`로 현재 섹션 강조.
  - 모바일: 본문 위 접힌 "목차".
- **코드 복사 버튼·언어 표시**: `RichContent`가 붙은 뒤, 링크 카드 처리 옆에서 각 `pre`에 `복사` 버튼과 언어 이름을 붙인다. 복사 후 "복사됨"을 잠깐 보여준다.

## 부록 A. DB 스키마 (insights)

```
insights
├─ id            UUID PK
├─ user_id       UUID FK → profiles
├─ title         TEXT NOT NULL
├─ content       TEXT NOT NULL        -- Tiptap JSON 문자열
├─ image_url     TEXT
├─ summary       TEXT                 -- 스키마상 nullable, 폼에서만 필수 강제 (D1로 해제 예정)
├─ slug          TEXT UNIQUE          -- 20260405142649, INSERT 트리거로 title 기반 자동 생성
├─ views         INTEGER DEFAULT 0    -- 20260517173500
├─ created_at    TIMESTAMPTZ
└─ updated_at    TIMESTAMPTZ

insight_comments  (parent_comment_id 지원 — 대댓글 O)
insight_likes     (UNIQUE(insight_id, user_id))
insight_bookmarks (PK(insight_id, user_id))
```

- **트리거**: INSERT 시 slug 생성, INSERT 시 활동 피드 생성(`create_activity_on_insight_created`), DELETE 시 활동 정리.
- **RLS**: SELECT는 누구나(`USING (true)`), INSERT·UPDATE·DELETE는 본인만.
- **없는 것**: `category`, `tags`, 초안 저장소, `published_at`, 팔로우 테이블.
- **계획된 변경 (§11 4단계)**: `insights.category`(체크 제약 5종), `insights.tags text[]`(GIN 인덱스), 새 테이블 `insight_drafts`(본인만 접근). 초안을 별도 테이블에 두므로 위 SELECT 정책과 트리거는 바꾸지 않는다.

> 참고: `summary`는 DB상 nullable이므로 **1-1 개선은 마이그레이션 없이 가능**하다.
